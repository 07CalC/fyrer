## No level barriers

Most monorepo runners schedule in levels: every task at depth *N* has to finish before depth *N+1* starts. fyrer schedules the graph itself — a task starts the instant its own dependencies succeed, whether or not its siblings are done.

## Why fyrer

<CardGroup cols={3}>
  <Card title="Streaming DAG" icon="bolt">
    Tasks start the instant their dependencies succeed, up to `concurrency`. `web:build` starts right after `ui:build` — it doesn't wait on `api:build`.
  </Card>
  <Card title="Content-addressed cache" icon="database">
    blake3 hashes `id + cmd + cwd + env + inputs`. Outputs archive as `tar.zst` relative to the workspace root and restore whole on a cache hit.
  </Card>
  <Card title="Language agnostic" icon="layer-group">
    If it runs in a shell, fyrer can schedule it. Mix Rust, Go, TypeScript, and Python tasks in one `fyrer.yml`.
  </Card>
  <Card title="Watch mode" icon="eye">
    `watch: true` polls `inputs` every 300ms, debounced, and restarts the task on change. Dependents flip to `↻ Stale` in the TUI.
  </Card>
  <Card title="Interactive TUI" icon="desktop">
    Per-task log panes. `r` restarts, `K` kills, `q` quits. Pass `-n` in CI for plain, prefixed logs instead.
  </Card>
  <Card title="Single binary" icon="cube">
    No daemon, no runtime to manage. Install with `install.sh` or `cargo install fyrer` — 6 prebuilt targets.
  </Card>
</CardGroup>

## How it works

<Steps>
  <Step title="Describe the graph">
    Put `fyrer.yml` at the repo root and list packages and tasks. `depends_on: [ui:build]` points at another package's task; a bare `build` means "my own build task."

    ```bash
    fyrer list          # every package:task
    fyrer plan build    # preview levels — for reading, not scheduling
    ```
  </Step>
  <Step title="Run it">
    ```bash
    fyrer run build -n   # CI: plain logs, exit code carries the result
    fyrer run dev        # TUI: every dev server, logs streaming live
    ```

    `api:build` and `ui:build` start together. `web:build` starts the moment `ui:build` succeeds, not when the level clears.
  </Step>
  <Step title="Iterate">
    Save a file and any `watch: true` task restarts on its own. Untouched `build` tasks hit `⚡ Cached` and restore their outputs instead of rebuilding.

    ```bash
    fyrer run build   # only what changed actually runs
    ```
  </Step>
</Steps>

<Columns cols={2}>
  <div>
    ### Built for watching a monorepo run

    | Key | Action |
    | --- | --- |
    | `q` / `Ctrl+C` | Quit, killing every process group |
    | `j`/`k` `↑`/`↓` | Select a task |
    | `u`/`d` `PgUp`/`PgDn` | Scroll that task's log |
    | `g`/`G` | Jump to top / tail |
    | `r` | Restart the selected task |
    | `K` | Kill the selected task |

    <Tip>
      In CI, run `fyrer run build -n`. Every line comes prefixed `[package:task]`, colorized per package, no TUI required.
    </Tip>
  </div>
  <div>
    ### Every option a task can take

    ```yaml
    tasks:
      build:
        cmd: bun build src --outdir dist
        inputs: [src/**, package.json]
        outputs: [dist/**]
        ignore: [node_modules/**]
        cache: true
        timeout: 5m
        cwd: subdir
        env: { NODE_ENV: production }
        env_file: .env.production
    ```

    fyrer validates all of it at startup: names are unique, `root`/`cwd`/`env_file` are relative paths that exist, `inputs`/`outputs` are valid globs, and `cache` never combines with `persistent` or `watch`.
  </div>
</Columns>
